# Конституция «Логопед+»

## Основные принципы

### I. Требования определяют поведение

Перед реализацией новой функции или изменением пользовательского поведения необходимо
описать цель, границы, сценарии и проверяемые критерии приёмки в спецификации.
Технические решения фиксируются в плане. Неоднозначности, влияющие на результат,
необходимо разрешить до реализации зависимой части. Результат проверяется по требованиям.

### II. Автономность основных операций

Основные операции с детьми и занятиями должны работать без сети.
Backend, серверная авторизация и синхронизация не входят в MVP.
Постоянное хранение пока не реализовано; его внедрение требует отдельной спецификации.
Нельзя представлять хранение в памяти как сохранение между запусками процесса.

### III. Границы слоёв и обоснованная сложность

Compose UI получает состояние и передаёт действия через ViewModel; доступ к данным
проходит через контракты репозиториев. UI не обращается напрямую к базе данных.
Новые зависимости, слои и изменения контрактов необходимо обосновать в плане,
проверив вызывающий код и потребителей. Room, Hilt, Navigation Compose и use cases
из целевого плана не требуется внедрять попутно с каждой функцией.

### IV. Проверяемые изменения

Изменения логики должны сопровождаться подходящими автоматизированными проверками
пользовательских правил или регрессии. Android-зависимые сценарии проверяются на
устройстве/эмуляторе, когда это необходимо; отсутствие среды фиксируется как ограничение.
В отчёте необходимо различать выполненные, упавшие и не запущенные проверки.
Команды и правила проверок определены в [AGENTS.md](../../AGENTS.md).
Шаблонные Example*Test не доказывают выполнение критериев приёмки.

### V. Актуальность документации

Спецификация описывает требуемое поведение, исходники — фактическую реализацию,
карта пакетов — навигацию по коду. Расхождения необходимо исправлять явно;
нельзя менять требования только для оправдания ошибки реализации.
При изменении структуры исходников необходимо обновлять PACKAGES.md и PACKAGE.md.
Проектные документы пишутся по-русски и отделяют текущее состояние от планов.

## Ограничения и технический контекст

Проект — Android-приложение на Kotlin и Jetpack Compose с одним модулем app.
Подтверждённое состояние и целевые решения разделены в
[ARCHITECTURE.md](../../ARCHITECTURE.md). Версии SDK и библиотек определяются Gradle-файлами.
Конституция задаёт правила дальнейших изменений и не объявляет целевую архитектуру реализованной.

## Процесс разработки

Для изменения поведения: спецификация → уточнения → план → задачи → анализ
согласованности → реализация → проверка критериев приёмки.
План должен содержать проверку применимых принципов этой конституции.
Задачи должны связывать требования, реализацию и проверки.
Опечатки, правки документации и рефакторинг без изменения поведения не требуют
отдельной полной спецификации; необходимы описание границ и подходящая проверка.
При изменении существующего поведения spec.md поддерживается как актуальный контракт,
а связанные план, задачи и проверки согласуются в том же изменении.
Рабочий маршрут: [SDD.md](../../SDD.md).

## Управление правилами

Конституция задаёт общие правила проекта; AGENTS.md описывает их выполнение.
Конфликт проектных документов необходимо обозначить и устранить.
Изменение принципа фиксируется здесь с причиной и оценкой влияния на активные спецификации.
Исключение должно быть явно описано и согласовано в рамках задачи.
Версия меняется по SemVer: MAJOR — несовместимое изменение принципов,
MINOR — новый принцип или существенное расширение, PATCH — уточнение без изменения смысла.
Перед завершением работы проверяется соответствие применимым принципам.
