# Проверка функции сохранения детей

Это руководство для будущей реализации [плана](plan.md); перечисленные новые тесты сейчас не созданы. Поведение: [контракты](contracts/children.md), данные: [модель](data-model.md).

## Среда

Использовать корень slt-mobile, JDK для текущего Gradle/AGP, установленный Android SDK 37 и тестовое устройство/эмулятор API 34+. Для проверки перезапуска нужен adb. Чистую установку выполнять на отдельном тестовом эмуляторе без пользовательских данных; не очищать рабочую установку пользователя.

## Сборка и автоматизированные проверки

В начале реализации проверить разрешение новой цепочки генерации DAO и версий:

```powershell
.\gradlew.bat :app:dependencyInsight --dependency kotlinx-coroutines-core --configuration debugRuntimeClasspath
.\gradlew.bat :app:assembleDebug
```

Ожидание: Room DAO сгенерирован, схема v1 экспортирована, debug APK собран; coroutines-test закреплён на совместимой с core версии. Если разрешение зависимостей не удалось, зафиксировать конкретную причину, не считать совместимость проверенной.

После реализации:

```powershell
.\gradlew.bat :app:testDebugUnitTest
.\gradlew.bat :app:connectedDebugAndroidTest
```

## Проверка процесса и устройства

1. Установить сборку на чистый тестовый эмулятор. Без сети открыть «Дети» и расписание: оба списка пусты. Перезапустить 5 раз без ввода: примеры не появляются (SC-005).
2. Добавить 20 детей, в том числе двух с одинаковым именем; одно имя ввести с крайними пробелами. Записать ожидаемый порядок. Каждый раз дождаться закрытия формы после успешной записи.
3. Пять раз завершить процесс и открыть приложение; затем перезагрузить устройство и открыть приложение снова. Число записей — 20, имена/порядок неизменны, тёзки отдельны (SC-001). Для тестовой установки:

```powershell
adb shell am force-stop com.logoped_plus
adb shell am start -n com.logoped_plus/.MainActivity
```

Перезагрузку тестового устройства можно выполнить его обычным меню. Проверять реальный новый процесс, а не только возврат на экран.

4. Создать занятие с одним ребёнком, переименовать его: новое имя видно в списке и занятии, состав участников прежний. После завершения процесса проверить имя в списке и выборе участников нового занятия; сохранность самого занятия не ожидается (SC-002).
5. Проверить отмену, пустой ввод, ошибку записи и повтор на тестовой подмене с контролируемой ошибкой. Нет лишних изменений; ввод сохранён, успешный повтор создаёт ровно одну запись (SC-003).
6. Воспроизвести ошибку чтения через тестовую подмену при открытой форме ребёнка: сообщение и «Повторить загрузку» доступны внутри диалога, имя/ID сохранены, запись недоступна. Нажатие запускает только чтение; после Ready подтвердить сохранение отдельно и проверить ровно одну запись. Повторить ошибку без открытой формы: повтор доступен на основном экране, дети не заменены примерами (SC-004).
7. Для FR-009 выполнить протокол управляемого прерывания ниже. Ранее подтверждённые записи остаются. Не пытаться вызвать сбой заполнением диска рабочего устройства.

## Управляемое прерывание реальной транзакции

Стенд создаётся в T020: TransactionProbeService только в debug, отдельный процесс приложения с DUMP permission, отдельный файл БД. Сервис отсутствует в release; debug-размещение позволяет вызывать реальные Room-классы приложения без classloader-подмены из instrumentation APK. Внешний PowerShell-драйвер `scripts/check-transaction-interruption.ps1` управляет запуском, ожидает сигналы с уникальным ID прогона и завершает только процесс стенда. Контроллер не должен находиться в завершаемом процессе. Production-приложение и его children.db не используются.

1. Создать контрольную запись и подтвердить её commit. Для проверяемой вставки/переименования вызвать реальный ChildDao внутри внешней Room-транзакции того же экземпляра БД; вложенная операция должна оставаться частью этой транзакции.
2. Режим BEFORE_COMMIT: после выполнения SQL, но до выхода из внешней транзакции, сообщить сигнал драйверу и ждать разрешения. Драйвер завершает процесс без корректного закрытия БД. Новый процесс открывает тот же файл: вставленной строки нет, при переименовании осталось прежнее имя, контрольная запись цела. Пауза перед вызовом DAO не заменяет эту точку.
3. Режим AFTER_COMMIT: выйти из внешней транзакции, затем сообщить сигнал и ждать до выдачи пользовательского результата. Завершить процесс; новый процесс читает полностью новое состояние, без дублей, контрольная запись цела.
4. Для обоих режимов выполнить вставку и переименование. Отдельно обычным путём repository подтвердить Success, завершить процесс и проверить восстановление записи. Проверки UI и fake-ошибок не заменяют этот файловый стенд.
5. Драйвер должен проверять PID/имя процесса стенда перед завершением, иметь таймаут ожидания сигнала и сохранять режим, ID прогона и результаты повторного чтения в validation.md. Отсутствие сигнала означает непрошедший/незапущенный сценарий, а не успех. Очистка касается только файла данного теста после завершения проверки.

Ожидаемые старое/новое состояния здесь точнее общей гарантии FR-009, поскольку момент остановки управляем. Стенд проверяет восстановление реального файла при смерти процесса; обычный пользовательский путь add/update отдельно покрыт тестами repository и перезапуском приложения.

## Документация и отчёт

Проверить охват package и относительные ссылки в PACKAGES.md/PACKAGE.md, экспорт схемы и отсутствие предзаполненных детей/занятий в production. Выполнить git diff --check. Example*Test не засчитывать как приёмку.

Отдельно перечислить выполненные, упавшие и не запущенные проверки. Если устройства нет, явно оставить Android UI, файловую БД и перезагрузку непроверенными; локальные тесты их не заменяют.
