# Исследование технических решений

Дата: 2026-09-09. Основание: [spec.md](spec.md). Исследование выполнено по исходникам и официальной документации; зависимости не устанавливались, совместимость сборкой не подтверждалась.

## 1. Локальное хранение

**Решение**: Room 2.8.4, одна таблица детей, без начального заполнения.

**Причина**: Нужны точечное обновление, транзакции и наблюдение за данными. Room проверяет SQL при компиляции и поддерживает Flow. Это соответствует целевому направлению проекта, не требует внедрения всей целевой архитектуры. Android рекомендует Room поверх прямого SQLite API. [Руководство Room](https://developer.android.com/training/data-storage/room)

**Альтернативы**: SQLiteOpenHelper уменьшает число зависимостей, но требует ручного SQL, mapping, диспетчеризации и уведомлений об изменениях. DataStore не выбран для списка записей с индивидуальными обновлениями; хранение в памяти не удовлетворяет FR-001. [SQLite](https://developer.android.com/training/data-storage/sqlite), [DataStore](https://developer.android.com/topic/libraries/architecture/datastore)

## 2. Генерация кода и версии

**Решение**: runtime/compiler/testing Room 2.8.4, KSP2. Исходный baseline KSP `2.2.10-2.0.2`; проверить фактически разрешённые версии при AGP 9.4.0. Экспорт схемы через room.schemaLocation с CommandLineArgumentProvider; отдельный Room Gradle plugin не нужен.

**Причина**: Room 2.8 требует minSdk 23, линия Room 2.7+ требует Kotlin 2.0+, рекомендует KSP2. minSdk проекта 34. AGP 9 включает Kotlin и документирует минимальный KSP baseline, но эта документация не доказывает совместимость всей комбинации с AGP 9.4.0. Compose plugin 2.2.10 сам по себе не устанавливает версию встроенного компилятора AGP. [Room releases и настройка схем](https://developer.android.com/jetpack/androidx/releases/room), [AGP 9](https://developer.android.com/build/releases/agp-9-0-0-release-notes)

**Проверка решения**: в начале реализации выполнить dependencyInsight для coroutines-core, генерацию DAO и assembleDebug. Версию coroutines-test согласовать с разрешённым core. При несовместимости KSP выбрать поддерживаемую версию по официальным требованиям фактического компилятора и записать её в каталог/план; не отключать встроенный Kotlin и не понижать AGP вслепую.

**Альтернативы**: KAPT не выбран из-за ограничений built-in Kotlin; прямой SQLite не используется как обход непроверенной сборки. Обновление всех зависимостей не относится к функции. [Переход на built-in Kotlin](https://developer.android.com/build/migrate-to-built-in-kotlin)

## 3. Асинхронность, ошибки и повтор

**Решение**: suspend для записи, DAO Flow для наблюдения, единый StateFlow с Loading/Ready/Error в repository. Retry пересоздаёт подписку после ошибки. Ошибка чтения после commit не меняет успех записи.

**Причина**: Room предоставляет асинхронные записи и наблюдаемые запросы. Пустой список не выражает сбой, поэтому контракт расширяется. Не выполнять отдельные запросы по каждому ID в ScheduleViewModel. [Асинхронные запросы Room](https://developer.android.com/training/data-storage/room/async-queries)

**Альтернативы**: синхронные методы с диском блокируют UI; оптимистический список может показывать несохранённые данные; ручной refresh после каждого сохранения дублирует наблюдение.

Состояние Saving устанавливается до запуска coroutine. UUID принадлежит форме и повторяется при retry. Транзакционная проверка ID делает повтор добавления безопасным. Это проектное решение для FR-004/009, а не автоматическая гарантия Room.

## 4. Владение и жизненный цикл

**Решение**: Application-контейнер с одной БД/repository на процесс; редактор в ChildrenViewModel. Запись запускается из ViewModel, а не из coroutine отдельной композиции. CancellationException не перехватывается как ошибка хранения.

**Причина**: текущий remember в App не является владельцем процесса. Общий scope сохраняет наблюдение между экранами; ViewModel сохраняет редактор при пересоздании Activity. Процесс может оборваться — это покрывается атомарной записью, а не обещанием завершить coroutine после смерти процесса. [Coroutines и жизненный цикл](https://developer.android.com/topic/libraries/architecture/coroutines), [Практики coroutines](https://developer.android.com/kotlin/coroutines/coroutines-best-practices)

**Альтернативы**: Hilt добавляет лишний объём; отдельная БД для каждой ViewModel усложняет владение; GlobalScope не нужен.

## 5. Порядок и удаление примеров

**Решение**: служебный AUTOINCREMENT position и уникальный UUID; UPDATE имени не меняет position. Production InMemoryChildRepository удалить; InMemoryLessonRepository оставить пустым для текущих пользовательских занятий.

**Причина**: FR-002 требует порядок добавления независимо от времени устройства. Пользователь явно отверг прежние данные. Начальные занятия также удаляются, включая их комментарии, чтобы не оставить ссылки на прежних детей.

**Альтернативы**: сортировка по имени/UUID не сохраняет порядок; начальная загрузка примеров противоречит FR-008. Тесты создают свои фикстуры явно, не зависят от production seed.

## 6. Доказательство сохранности

**Решение**: instrumented test файловой БД с закрытием и повторным открытием; дополнительно ручная проверка завершения процесса/перезагрузки. Ошибки и задержки детерминированно моделируются тестовыми DAO/repository, без порчи пользовательского устройства.

**Причина**: Android рекомендует тесты БД на устройстве. In-memory Room удобен для изоляции запросов, но не доказывает постоянное хранение. [Тестирование Room](https://developer.android.com/training/data-storage/room/testing-db)

**Альтернативы**: Example*Test и проверка только повторного открытия экрана не подтверждают FR-001. Все технические решения приняты; остаётся выполнить запланированные проверки при реализации.

## Проверенная конфигурация реализации

Исходный KSP 2.2.10-2.0.2 вызвал ошибку kotlin.sourceSets со встроенным Kotlin AGP. Выбран KSP 2.3.10 ([официальные релизы](https://github.com/google/ksp/releases/tag/2.3.10)); DAO и оба APK успешно собраны с AGP 9.4.0/Room 2.8.4. DependencyInsight установил coroutines-core 1.9.0, coroutines-test согласован на 1.9.0. Стенд транзакций находится только в debug source set, отдельно от release, поскольку самостоятельный сервис instrumentation APK не имеет обычного доступа к классам target APK.
