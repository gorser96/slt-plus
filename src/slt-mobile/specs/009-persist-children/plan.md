# План реализации: Сохранение детей в БД

**Ветка Git**: `main` | **Дата**: 2026-09-09 | **Спецификация**: [spec.md](spec.md)

**Контекст Spec Kit**: `009-persist-children`. setup-plan вернул это значение в BRANCH как идентификатор каталога; фактическая ветка проверена через Git. Новая ветка не создавалась.

**Уточнения после анализа**: миграция контракта и компилируемый каркас предшествуют проверке падения тестов; при открытом редакторе повтор чтения доступен внутри диалога; граница commit проверяется отдельным тестовым процессом по протоколу quickstart.

## Краткое описание

Заменить хранение детей в памяти локальной Room БД. Сохранить правила добавления и переименования, добавить состояния загрузки, ошибки и сохранения. Удалить все предзаполненные данные детей и занятий. Пользовательские занятия остаются в памяти текущего процесса.

Обоснования: [research.md](research.md); схема: [data-model.md](data-model.md); интерфейсы: [contracts/children.md](contracts/children.md); приёмка: [quickstart.md](quickstart.md). Это проектирование, а не отчёт о реализации.

## Технический контекст

- **Язык/сборка**: Kotlin; Compose compiler plugin 2.2.10, AGP 9.4.0, Gradle 9.6.0, Java source/target 11. Версия встроенного Kotlin AGP определяется отдельно от версии Compose plugin.
- **Текущие зависимости**: Compose BOM 2026.02.01, ViewModel Compose 2.11.0, Coroutines/Flow. Навигация на состоянии Compose, ручная сборка зависимостей.
- **Новые зависимости**: Room runtime/compiler/testing 2.8.4, KSP2; проверенная версия KSP `2.3.10`, с учётом ограничений встроенного Kotlin AGP. kotlinx-coroutines-test согласовать с фактически разрешённой версией coroutines-core. Версии фиксировать в каталоге, без попутного обновления остальных библиотек.
- **Хранилище**: приватный файл `children.db`, версия 1, таблица `children`; без seed и destructive fallback.
- **Проверки**: JUnit для ViewModel, Android instrumented tests для файловой БД и Compose; отдельно перезапуск процесса и устройства.
- **Платформа/тип**: Android-приложение, один модуль app; minSdk 34, compileSdk/targetSdk 37.
- **Производительность**: SQL и открытие файла вне main thread; асинхронные Room API. Численные SLA не добавляются.
- **Масштаб**: один пользователь/устройство, приёмочный набор из 20 детей с тёзками.
- **Ограничения**: без сети, переноса старых данных, новых полей и удаления пользовательских записей. Существующие настройки Android backup не считаются реализацией резервного копирования; новых гарантий переноса между устройствами нет.

### Найденная цепочка и фактическое поведение

`ChildrenScreen → ChildrenViewModel → ChildRepository → InMemoryChildRepository → Child`. Форма сейчас закрывается сразу, методы синхронные, начальных детей три. App создаёт repository через remember, что не подходит для владельца общей долговечной БД.

ScheduleViewModel читает children.value и getChildById. Удалить синхронный поиск из контракта: преобразовывать занятия по карте ID из одного успешно загруженного снимка. Проверены родительский ScheduleScreen и его маршруты создания, редактирования, сохранения комментариев/видео.

## Последовательность реализации

1. Проверить разрешение Room/KSP с текущим AGP, генерацию DAO и debug-сборку; добавить схему v1. Не обходить проблемы main-thread queries или разрушением данных.
2. Сначала согласованно ввести контракт, адаптировать сигнатуры потребителей и подготовить компилируемый каркас RoomChildRepository/редактора для тестов. После содержательного падения тестов реализовать один общий eager StateFlow в scope контейнера и повтор подписки после ошибки; без оптимистического изменения списка. Подготовительная часть T009/T010 предшествует T007/T008, завершение — после них.
3. Подключить Application-контейнер и одинаковые зависимости обеим ViewModel. Ошибка открытия файла должна стать Error асинхронного чтения, а не падением App.
4. Перенести редактор детей в ViewModel. Установить Saving до launch; сохранить ID при повторе; закрывать только по Success. CancellationException не маскировать под ошибку записи.
5. Адаптировать расписание: на Loading/Error блокировать выбор и все записи занятий также в ViewModel, оставить просмотр и черновики. Ready обновляет имена без изменения связей.
6. Удалить production-примеры. InMemoryLessonRepositoryTest должен сам добавлять исходное и соседнее занятия вместо before.first() на начальном наборе. Тестовые фикстуры не возвращать в production.
7. Выполнить quickstart и обновить PACKAGES.md, затронутые PACKAGE.md, текущий раздел ARCHITECTURE.md, SDD.md и индекс спецификаций. Ретроспективные документы сохраняют историческое основание с явной ссылкой на новый контракт.

## Риски и меры

| Риск | Решение/проверка |
|---|---|
| Дубликат при повторе | Saving до launch, стабильный UUID, идемпотентная вставка; тесты задержки/повтора |
| Commit успешен, чтение упало | Раздельные результаты записи и чтения; не возвращать ошибку записи после подтверждённого commit |
| Пересоздание Activity | Application-контейнер, редактор в ViewModel; recreation test |
| Подписка умерла | RetryChildren пересоздаёт DAO Flow; Error → Loading → Ready |
| Ошибка принята за пустой список | Ready(emptyList) отличается от Loading/Error |
| Тесты зависели от примеров | Явные фикстуры и тест пустого начального repository |

## Учёт сложности

Нарушений конституции нет. Контейнер нужен для единого владельца БД, Room — для SQL/транзакций/наблюдения, состояния — для различения ошибок и пустого результата. Новых модулей, DI-фреймворка и сервера не требуется.
