# Design

## Context

См. proposal.md. Фактическое состояние: видео прикрепляются только через SAF-пикер (`VideoAttachmentsEditor`, постоянный URI-grant), изменения списка живут в черновике редактора (`LessonEditorState`) и применяются при явном сохранении через атомарный `updateLesson` (Room-транзакция, уникальность URI). Разрешений на медиа в манифесте нет, use case-слоя в коде нет (ViewModel → repository), `minSdk = 34`. Кнопка — в разделе видео деталей; компонент общий для деталей и редактирования.

## Goals / Non-Goals

**Goals:**

- Поиск видео на устройстве по интервалу занятия и добавление найденных в черновик списка видео деталей/редактирования.
- Чистое, тестируемое без Android правило «видео в интервале занятия без дубликатов».
- Безопасная работа с разрешением на медиа и сообщениями о результатах.

**Non-Goals:**

- Съёмка, перенос между занятиями (открепление от других занятий), выбор из найденного списка, повторный поиск по нескольким занятиям разом.
- Изменение схемы БД, правил сохранения, порядка ссылок.
- Оптимизация скана под большие библиотеки видео.

## Decisions

Применимые решения ARCHITECTURE.md: §18 (видео — ссылки, работа с разрешениями), §23 (Presentation → Domain, Domain без Android, Data с Android), §5/§25 (бизнес-правило не в ViewModel), §9/§24 (use case как законченная операция), §26 (минимальные проверки).

1. **Кнопка в `VideoAttachmentsEditor`, результат — в черновик.** Кнопка вызывает новое действие `ScheduleAction.AutoAttachLessonVideos(sessionId)`; найденные URI добавляются в `videoUris` черновика тем же путём, что и выбор из пикера, и применяются только при сохранении (`ConfirmLesson`). Альтернатива — немедленная запись из деталей — отклонена: ломает инварианты редактора (черновик — копия сохранённого агрегата, блокировки Saving, `sessionId`) и противоречит требованиям «Явное сохранение связей» и «Отмена без записи».
2. **Domain: модель + контракт + use case.** `DeviceVideo(uri, displayName?, createdMillis)` — в `domain.model`. Контракт `VideoLibrary { suspend fun findVideos(from: Instant, to: Instant): List<DeviceVideo> }` — в `domain.repository` (контракт доступа к данным, аналог repository). `FindLessonVideosUseCase` — новый пакет `domain.usecase`: вычисляет интервал занятия в эпоху и отбирает видео без дубликатов. Альтернативы: правило в ViewModel (запрещено §5/§25) или в сканере Data (бизнес-правило вне Domain). Use case вводится впервые и только под это правило — оно ядро функции и проверяется unit-тестом без Android.
3. **Data: `MediaStoreVideoScanner` в новом пакете `data.media`.** Одна выборка из `MediaStore.Video.Media.EXTERNAL_CONTENT_URI` (ID, DISPLAY_NAME, DATE_TAKEN, DATE_ADDED) на IO; время создания = `DATE_TAKEN` (если > 0), иначе `DATE_ADDED`. Интервал фильтруется в памяти: точный интервал с fallback в SQL не выразить, объём библиотеки на устройстве мал. Сканер и use case создаёт `AppContainer` (контекст уже есть), передаёт `ScheduleViewModelFactory` → `ScheduleViewModel`.
4. **Интервал и время.** `[start, start + durationMinutes)`: начало включительно, конец не включительно (видео в момент конца занятия относится следующему интервалу). `LocalDateTime` → эпоха через `ZoneId.systemDefault()`; значения MediaStore в секундах. Занятие, переходящее через полночь, покрывается одним интервалом эпохи без особых правил.
5. **Разрешение.** `READ_MEDIA_VIDEO` в манифесте (minSdk 34 — legacy-разрешения не нужны). Компонент проверяет разрешение до действия: нет — `rememberLauncherForActivityResult(RequestPermission())` с тем же сессионным guard, что у пикера (`enabled` + `sessionId`); отказ — локальное сообщение об ошибке. Поиск выполняется в ViewModel (скан вне UI-потока), действие игнорируется при `saving`.
6. **Состояние и сообщения.** В `ScheduleUiState`: `videoScanInProgress` (кнопка неактивна, повторное нажатие не запускает второй поиск) и `videoScanMessage` (итоги: добавлено N / не найдены / ошибка значений; сбрасывается при новом поиске и смене редактора). Интервал берётся из `editor.toLesson()` — значений, отображаемых в форме: в DETAILS это сохранённые значения, в EDIT — текущие raw-поля; некорректные значения дают сообщение без поиска.
7. **Хранение без изменений.** Черновик сохраняется существующим `updateLesson`; уникальность URI уже проверяется. Ссылки MediaStore поддерживают открытие через существующий `VideoAttachmentLink` (ACTION_VIEW с grant), пока действует разрешение на медиа; постоянный URI-grant источником не поддерживается — при отзыве разрешения срабатывают стандартные сообщения о недоступном файле, открепление остаётся (сценарий 9 дельты).

## Risks / Trade-offs

- [Ссылки MediaStore без постоянного доступа: отзыв разрешения делает их неоткрываемыми] → зафиксировано в дельте: стандартная ошибка, ссылка и открепление сохраняются; до отзыва разрешения доступ гарантирован.
- [Полный скан библиотеки при каждом поиске] → одна выборка на IO-потоке; приемлемо для MVP, префильтр SQL — будущая оптимизация.
- [У файла может не быть `DATE_TAKEN` (перекинутые записи)] → fallback на `DATE_ADDED`; точность «создания» деградирует до времени появления на устройстве.
- [ROM может нарушать контракт MediaStore по единицам времени] → подтверждено на OnePlus PJE110 (OxygenOS): `DATE_TAKEN` в миллисекундах при `DATE_ADDED` в секундах; сканер нормализует единицы через `mediaStoreTimeToMillis` (порог 1e11: миллисекунды до 1973 меньше, секунды достигают 1e10 лишь после 2286).
- [Эмулятор и connected-тесты отключены (конфиг 2026-09-30)] → реальное поведение разрешения и MediaStore не проверяется автоматически; в `openspec/verification/README.md` фиксируется ручная приёмка.

## Проверки

- Новый unit-тест `FindLessonVideosUseCase` (test/): границы интервала (старт включительно, конец не включительно), дубликаты из черновика, пустой результат, занятие через полночь.
- Существующие unit-тесты: `.\gradlew.bat :app:testDebugUnitTest`.
- Сборка для контроля компиляции: `.\gradlew.bat :app:assembleDebug`.
- connected-тесты и эмулятор не запускаются; разрешение, MediaStore и UI — ручная приёмка.

## Migration Plan

Миграция не требуется: схема БД и хранимые данные не меняются; изменение обратно совместимо (откат — удаление кнопки и новых классов, без влияния на данные).
