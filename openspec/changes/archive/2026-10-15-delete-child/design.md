# Design

## Context

Дети и занятия живут в Room `children.db` (v2): `children` (position, id — уникальный индекс, name), `lessons`, `lesson_participants` (PK `lessonId`+`childId`, FK→lessons CASCADE, FK→children **RESTRICT**), `lesson_videos` (FK→lessons CASCADE). Удаление ребёнка сейчас невозможно: FK RESTRICT отклонит `DELETE FROM children` при живых ссылках. `LessonDao` — транзакционные `addOnce`/`updateExisting` (валидация `invalidReason`, проверка `knownChildren`), `deleteExisting` для занятий. Модель `Lesson(childIds: List<String>, ...)` — только ID; имена участников разрешает UI из `ChildLoadState` (`ScheduleViewModel.toUiModel`).

Договорённости: `ChildRepository.state` (Loading/Ready/Error), `write()` в `RoomChildRepository` (trim, NotReady, CancellationException пробрасывается, исключение → StorageUnavailable); `ChildWriteResult.Reason` уже содержит NotFound. Паттерн удаления занятия (delete-lesson): команда в форме/деталях → диалог подтверждения → Saving-статус → результат.

Приложимые решения ARCHITECTURE.md: §10/§14 (контракт в Domain, реализация в Data), §15 (Room — источник истины, Flow обновит UI после удаления без ручных reload), §16 (offline-first, удаление ребёнка — локальная операция), §23 (Domain не знает Room), §26 (минимальные проверки под риск; миграции и сохранность данных требуют проверки). Use cases и Hilt в проекте отсутствуют — следуем фактическому стилю (ViewModel → repository).

## Goals / Non-Goals

**Goals:**
- удаление ребёнка из формы редактирования с диалогом подтверждения, по правилам delete-lesson (подтверждение, блокировки, ошибка, одна операция);
- занятия удалённого ребёнка сохраняются целиком и остаются в расписании с именем ребёнка на момент удаления;
- миграция БД v2→v3 с сохранением всех пользовательских данных;
- правила записи занятий учитывают «исторических» участников: занятие с ними остаётся валидным и сохраняемым.

**Non-Goals:**
- восстановление/возврат удалённого ребёнка, пакетное удаление, удаление из карточек списка,
- отображение «исторических» участников в выборке (они недоступны для выбора),
- экспорт/резервное копирование, изменения полей `Child`, перенос занятий между детьми.

## Decisions

1. **Data: снять FK участников на `children`, добавить поле снимка имени.** `lesson_participants` v3: `childName TEXT` (NULL для актуального участника) и без FK на `children`; FK на `lessons` (CASCADE), PK `(lessonId, childId)`, индексы и `childId NOT NULL` сохранены.
   - Альтернатива — `childId` nullable + `ON DELETE SET NULL`: отклонена — nullable-столбец внутри PK `(lessonId, childId)` требует переделки PK/схемы и Room-валидации; «висящий» id допустим как историчесная ссылка, целостность новых ссылок уже держит проверка `knownChildren` при записи.
   - Альтернатива — удалить строки участников при удалении ребёнка: отклонена — занятие теряет «кто», одиночное занятие становится невалидным (пустые участники) и не сохраняемым; против требования «занятия хранятся как история».
   - Альтернатива — мягкое удаление (флаг в `children`): отклонена — «удаление» перестает быть удалением, флаг нужно дублировать во всех фильтрах (список, выбор, расписание), рост концепций.

2. **Инвариант снимка: `childName` NULL ⟺ ребёнок существует.** `toDomain` мапит `childName` напрямую в модель; имя актуального ребёнка всегда берётся из `ChildLoadState` (переименование продолжает работать — persist-children SC-002), снимок — только для удалённых. Снимок делается в той же транзакции, что и удаление (атомарность по аналогии с persist-children «Атомарность при прерывании»).

3. **Домен: `Lesson.participants: List<LessonParticipant>`, `LessonParticipant(childId: String, removedName: String? = null)` в порядке занятия.** Заменяет `childIds` во всех слоях (маппинг, валидация, редактор, UI):
   - `invalidReason`: непустой список, непустые уникальные `childId`;
   - `knownChildren` проверяются только для актуальных участников (`removedName == null`);
   - `insertRelations` пишет всех участников (актуальные с NULL-именем, исторические со снимком) в порядке списка;
   - редактор занятия хранит участников; выбор (picker) оперирует только актуальными, исторические передаются в сохранение без изменений — редактирование занятия не теряет исторических участников;
   - `canSave`: каждый актуальный участник существует в списке детей, исторические проходят без проверки;
   - отображение: имя = снимок, иначе имя из `ChildLoadState`; число участников (типы «Групповое/Индивидуальное») — по всем участникам.

4. **ChildDao: транзакционное `deleteOnce(id): Boolean`.** `SELECT name` (нет → false/NotFound) → `UPDATE lesson_participants SET childName = :name WHERE childId = :id AND childName IS NULL` → `DELETE FROM children`. Снимок до удаления: в момент снимка ребёнок ещё существует. `RoomChildRepository.deleteChild` — по шаблону `write()`; результат — существующий `ChildWriteResult` (NotFound/NotReady/StorageUnavailable), новый тип не вводится (§25).

5. **Миграция v2→v3: пересоздание таблицы** (SQLite не снимает FK с существующей таблицы): `ALTER TABLE ... RENAME TO _old` → `CREATE TABLE` с DDL по v3-экспорту Room → индексы → `INSERT ... SELECT` с `childName = NULL` → `DROP _old`. Данные существующих участников не трогаются; `childName` заполняется только при фактическом удалении ребёнка. Регистрация `MIGRATION_2_3` в `ChildrenDatabase.create`, version 3, экспорт схемы 3.json. DDL миграции повторяет сгенерированную Room (проверяется по `app/schemas/.../3.json`).
   - Проверка миграции androidTest-инфраструктурой (RoomMigrationTestHelper) не выполняется: connected-тесты отключены настройками проекта; риск зафиксирован в Risks.

6. **Presentation (дети): состояние и действия в `ChildrenViewModel`.** `openDeleteConfirm(child)` (только Ready, не во время удаления; вызывается из формы редактирования существующего ребёнка), `cancelDelete()`, `delete()` (guard: не executing, Ready; `deleting=true` блокирует повтор/закрытие диалога; Success → закрыть диалог и форму, Failure(reason) → показать в диалоге). Поля состояния: `deleteTarget: Child?`, `deleting: Boolean`, `deleteError: Reason?`. Команда «Удалить» — в форме редактирования (рядом с «Отмена», только `!isNew`), диалог подтверждения — отдельный `AlertDialog` по образцу delete-lesson; текст диалога сообщает, что занятия сохранятся историей с именем.

7. **Presentation (расписание):** минимальная замена `childIds` → `participants`/`participantCount` в `LessonEditorState`, `ScheduleViewModel.toUiModel`, `ScheduleUiState.canSave`, `LessonUiModel`, карточках и деталях; поведение просмотра без изменения участников не меняется.

8. **Проверки — под риск потери/повреждения данных.**
   - JVM unit-тест новых правил `invalidReason` (занятие только с историческими участниками валидно; пустые/дубли id — InvalidData): чистая функция, дешевле БД-теста;
   - `:app:compileDebugKotlin` (компиляция всех слоёв, KSP-экспорт 3.json) + `:app:testDebugUnitTest` (регрессия);
   - `openspec validate delete-child --strict`;
   - Room-поведение (снимок имени, атомарность, миграция) локально не проверяется (эмуляторы отключены настройками проекта) — ручная приёмка остаётся открытой и фиксируется в `verification/README.md`;
   - новые ViewModel/Compose-тесты не вводят: поток — тонкое делегирование repository по существующим правилам Saving (аналог решения delete-lesson).

## Risks / Trade-offs

- [Миграция v2→v3 не протестирована автоматически (connected-тесты отключены)] → DDL совпадает с Room-экспортом 3.json, паттерн повторяет существующий `MIGRATION_1_2`; ручная приёмка на устройстве обязательна перед закрытием изменения.
- [Снятие FK ослабляет защиту от «висящих» ссылок на уровне БД] → новые ссылки валидируются `knownChildren` при любой записи; «висящий» id возникает только по снимку при подтверждённом удалении; вероятность совпадения снятого id с новым UUID пренебрежимо мала.
- [Истатистика типа занятия меняется только для занятий с удалёнными детьми] → осознанно: исторический участник остаётся участником (решение согласовано с пользователем).
- [Занятие, где удалены все дети, остаётся в списке без «живых» участников] → допустимо как история: просматривается, редактируется (дата/комментарий/видео), в выборке детей не участвует.

## Migration Plan

Схема: v2 → v3 (`MIGRATION_2_3`), имя файла `children.db` и класс не меняются; seed и destructive fallback запрещены (persist-children). Откат — отмена коммита; данные пользователей миграцией не затрагиваются, откат версии приложения с v3-файлом вне сценария MVP (обновление только вперёд).
