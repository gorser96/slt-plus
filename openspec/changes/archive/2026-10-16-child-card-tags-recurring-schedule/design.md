# Design

## Context

Цель — [proposal.md](proposal.md). Проверена цепочка: `ChildrenScreen` → `ChildrenViewModel` → `ChildRepository` → `RoomChildRepository` → `ChildDao`; сейчас Child содержит только id/name, UI открывает AlertDialog, DAO наблюдает порядок position. `LessonDao.addOnce` проверяет UUID и участников, но не занятость; цикл addLesson не даёт атомарность пакета. БД фактически v3, AppContainer и навигация ручные. Разделы описывают `AppScreen` и `AppDrawer`.

Применяются ARCHITECTURE.md: Presentation → Domain ← Data, бизнес-правила вне ViewModel, Room — источник истины, Flow, offline-first, минимальные абстракции. Перед реализацией существующие карты пакетов используются как точки входа. Полный переход на Hilt/Navigation Compose не требуется.

## Goals / Non-Goals

**Goals:** единый атомарный агрегат карточки, предсказуемая генерация на актуальном состоянии БД, сохранность v3-данных, тестируемые без Android правила времени и конфликтов.

**Non-Goals:** изменение ручных операций занятий, фоновые серии, каскадное изменение созданных занятий при правке шаблона, перенос DI и навигации на новые библиотеки.

## Decisions

### 1. Модели и хранение

Domain: `Tag(id, name, colorKey)`, `WeeklyLessonSlot(id, dayOfWeek, startTime, durationMinutes)` и шаблон с ordered slots/endDate. Расширить агрегат Child назначениями tagIds и шаблоном с пустыми значениями по умолчанию, чтобы существующие клиенты имени/id продолжили работать. Названия и цвета получать из общего справочника, не копировать в детей.

Room v4: `tags` с уникальным нормализованным ключом названия, `child_tags` с составным PK и FK CASCADE на детей/тэги, `child_schedule` (childId PK/FK, endEpochDay), `child_schedule_slots` с FK, стабильным ID и ordinal. Дни хранить ISO 1–7, время — nanoOfDay в принятой локальной системе, цвет — стабильным ключом палитры. Взаимное пересечение строк допускается. `ChildDao` наблюдает целый агрегат транзакционно, сохранение заменяет назначения и шаблон вместе с именем; rename сохраняет остальные поля. Удаление ребёнка сохраняет существующий snapshot имён, новые связи удаляются по CASCADE.

Альтернатива — сериализовать список в поле ребёнка — хуже проверяет ссылки и усложняет удаление общего тэга. Отдельное дублирование names/colors в карточках создаёт риск рассинхронизации.

### 2. Domain-операции и транзакционная генерация

Добавить чистый планировщик в domain.usecase: вход — сохранённый шаблон, childId, фиксированный now и актуальные занятия; выход — новые занятия и счётчики. Сортировка, определение существующих и сравнение полуоткрытых интервалов соответствуют [спецификации](specs/child-recurring-schedule/spec.md). Точное совпадение childId/start учитывается до проверки конфликта, включая групповые занятия и любую длительность. При одинаковом старте строк первая побеждает, следующая становится «уже существует»; если первая конфликтует с БД, конфликтуют обе. Вычисление конца проверяет переполнение, валидация не допускает непредставимых дат/длительностей.

`GenerateChildLessonsUseCase` получает now через внедрённый Clock в локальной зоне устройства; repository-контракт принимает childId/now и возвращает typed success(counts)/failure. Реализация внутри одной Room-транзакции читает актуальные карточку и занятия, вызывает domain-планировщик, вставляет целые агрегаты занятий. Правила не дублируются в DAO/ViewModel. Это сериализует проверку и вставку с другими записями; повтор/конкурентный запуск перечитывает уже созданные записи. Старый `addLesson` не меняет разрешение ручных пересечений. Чтение всего расписания приемлемо для текущего MVP; при росте объёма допускается интервальная выборка с обязательным захватом переходов через полночь.

Альтернатива — спланировать по StateFlow и последовательно вызвать addLesson — оставляет окно гонки, частичные результаты и не годится. Уникальный индекс на время занятия запрещал бы допустимые ручные пересечения.

### 3. Контракты карточки и тэгов

Расширить ChildRepository атомарным обновлением полного агрегата, сохранив совместимость операций имени. Добавить TagRepository с Flow Loading/Ready/Error, typed write result, стабильным UUID черновика и идемпотентным повтором. Проверка пустого/дублирующего названия с trim и lowercase(Locale.ROOT), уникальный ключ в БД защищает от гонок; свои старые значения при редактировании разрешены. Палитра фиксированная, например 8 цветов со стабильными ключами; контрастные подписи вычисляются в UI. Удаление тэга и назначений — одна транзакция. Пропавший выбранный тэг удаляется из черновика, при записи повторно проверяется актуальность ссылок.

### 4. UI и навигация

В children-состоянии хранить выбранный childId, режим просмотра/редактирования, полный черновик, запрос и статус операции; UI не читает DAO. Добавление ребёнка остаётся простым диалогом имени, дальнейшие поля доступны в карточке. Создание занятий — только из сохранённого просмотра, без неявного сохранения черновика. Результат показывает три счётчика, карточка остаётся открытой. Сохранение карточки возвращает в просмотр. Удаление доступно из карточки с прежним подтверждением.

Список получает UI-проекцию: поиск с одного символа, Collator для ru-RU со сравнением без регистра, стабильный порядок тёзок по исходной position. Позиции в БД не перенумеровываются. Поиск выбора участников из create-lesson остаётся прежним.

Добавить Tags в ручные AppScreen/AppDrawer/App; отдельные экран, ViewModel и фабрика справочника. Общий AppContainer передаёт новые repositories/use cases. App учитывает Saving/Generating всех затронутых экранов в существующей блокировке меню и Back. Черновики и активные операции живут во ViewModel и не повторяются при повороте. Дополнительные библиотеки навигации — неоправданное расширение задачи.

## Risks / Trade-offs

- [Старые контракты требуют порядок добавления и диалог] → дельты меняют соответствующие требования; при синхронизации также обновить явно перечисленные устаревшие граничные условия и критерии, которые CLI автоматически не переносит.
- [Ошибка миграции/пакетной вставки теряет данные] → явная MIGRATION_3_4, exported schema, атомарные записи и проверки rollback; destructive fallback запрещён.
- [Пересекающиеся строки дают меньше занятий, чем строк шаблона] → разрешить редактирование, но применять детерминированный приоритет и показывать счётчики конфликтов.
- [Очень дальняя дата даёт большой пакет] → вычислять и записывать вне main, показывать занятость; не вводить произвольный бизнес-лимит периода. Переполнение обрабатывать как некорректные данные без частичной записи.
- [Нельзя выполнить Android-проверку БД в текущем режиме] → unit-проверки чистой логики, локальная SQLite/Room-проверка через Robolectric при совместимости сборки; если это невозможно, явно оставить миграцию/rollback непроверенными в verification. Эмуляторы и connectedDebugAndroidTest отключены конфигурацией проекта.

## Migration Plan

1. Добавить новые таблицы в MIGRATION_3_4 без пересоздания children/lessons/participants/videos; для существующих детей назначения и шаблоны пусты. Сохранить позиции, ID, комментарии, URI и исторические имена.
2. Зарегистрировать всю цепочку 1→2→3→4 и обновить exported schema. Проверить на непустой v3-БД, включая удалённых участников.
3. Проверки реализации: адресные существующие unit-тесты; новые domain-тесты примера октября, now/end границ, дублей/повтора, глобальных конфликтов/полуночи и приоритета строк. Один достаточный локальный интеграционный набор для миграции и атомарности карточки, отвязки тэга и генерации, включая rollback и повтор. При необходимости добавить test-only Robolectric вместо запуска устройства.
4. Собрать debug, выполнить ручной осмотр состояния UI/Back/блокировок и обновить PACKAGE.md/PACKAGES.md. Результаты и реально недоступную приёмку зафиксировать в openspec/verification.
5. Откат релиза — восстановление из заранее сохранённой копии v3 при контролируемой проверке; downgrade с очисткой БД не допускается. При сбое открытия пользователю показывается ошибка без удаления файла.
