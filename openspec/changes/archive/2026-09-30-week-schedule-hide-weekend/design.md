# Design

## Context

Недельная сетка целиком в Presentation: `WeekScheduleView.kt` жёстко рисует 7 столбцов (`List(7)` для таймлайнов, `repeat(7)` для заголовков), а `buildWeekDayTimeline` (WeekTimeline.kt) считает таймлайн одного дня и клиппингует span'ы по границам дня — от числа столбцов не зависит. Экран настроек — заглушка: `SettingsScreen()` показывает один Text (проверено по коду).

DI ручной: `AppContainer` создаёт репозитории, экраны получают ViewModel через фабрики (`ScheduleViewModelFactory`, `ChildrenViewModelFactory`), use cases и Hilt в проекте нет. Единственный фактический автотест — `WeekTimelineTest` (JVM); androidTest и тесты, перечисленные в картах пакетов, в исходниках отсутствуют.

Приложимые решения ARCHITECTURE.md: §11/§15 (локальное хранение — Data, реактивные Flow), §25 (не создавать абстракции без необходимости), §26 (минимальные проверки: чистую тривиальную логику автотестом не покрывать).

## Goals / Non-Goals

**Goals:**
- переключатель «Скрывать выходные» на экране настроек;
- сохранение значения между запусками, по умолчанию — выходные показаны;
- недельная сетка: 5 столбцов (пн–пт) при включённой настройке, 7 иначе, с реактивным обновлением;
- занятость скрытых дней не видна в сетке, включая часть занятия после полуночи.

**Non-Goals:**
- месячный режим и дневной список (выходные там остаются как есть);
- подневные настройки (суббота и воскресенье настраиваются одним тумблером);
- быстрый тумблер на экране расписания — отклонено, настройка в разделе настроек;
- новые зависимости (DataStore и т. п.).

## Decisions

1. **`SettingsStore` в Data — не Repository и не Use Case.** Новый пакет `com.logoped_plus.data.preferences`: класс `SettingsStore(context)` обёртывает `SharedPreferences` (файл `settings`, ключ `hide_weekend`, дефолт `false`) и держит `hideWeekend: StateFlow<Boolean>`; `setHideWeekend(Boolean)` пишет в prefs и в flow. Один экземпляр создаёт `AppContainer`.
   - Не Repository/UseCase/Domain-контракт: одиночный boolean не оправдывает слой (ARCHITECTURE.md §25); это источник данных, а не контракт предметной области.
   - Альтернатива DataStore — отклонена: новая зависимость ради одного значения; SharedPreferences входит в платформу.
   - Альтернатива — класс в корневом пакете `com.logoped_plus` — отклонена: пакет «запуск/DI/навигация», предпочтения — Data (§11).

2. **Экран настроек — `SettingsViewModel` по существующему паттерну.** В пакете `com.logoped_plus.ui.screen` (рядом с `SettingsScreen.kt`): `SettingsUiState(hideWeekend: Boolean)`, `SettingsViewModel(settings: SettingsStore)` с функцией `setHideWeekend(Boolean)` и подпиской на `settings.hideWeekend`, фабрика `SettingsViewModelFactory` — как у `ChildrenViewModel`. `App.kt` создаёт ViewModel через фабрику и передаёт в `SettingsScreen(viewModel)`. UI: заголовок «Расписание» и `Switch` «Скрывать выходные» с пояснением про недельную сетку.
   - Альтернатива — stateless-комposable без ViewModel (как сейчас) — отклонена: состояние должно пережить поворот и быть единым на раздел, как у других экранов.

3. **Расписание — флаг в `ScheduleUiState`, подписка в `ScheduleViewModel`.** `ScheduleViewModel` получает третий параметр `settings: SettingsStore`; в `init` отдельный `viewModelScope.launch` собирает `settings.hideWeekend` и делает `copy(weekendHidden = …)`, начальное значение — из `settings.hideWeekend.value`. `ScheduleViewModelFactory` и `App.kt` дополняются параметром. `ScheduleScreen` передаёт флаг в `WeekScheduleView(weekendHidden = …)`.
   - Альтернатива — читать настройку в Composable через `LocalContext` — отклонена: нарушает правило «UI не читает данные напрямую» и дублирует источник.

4. **`WeekScheduleView` — 5/7 столбцов по флаго.** `val dayCount = if (weekendHidden) 5 else 7`; `timelines` строится `List(dayCount)`, заголовки и колонки — `repeat(dayCount)`. Подпись диапазона недели (`formatWeekRange`) не меняется — показана вся неделя, просто два дня не отображаются. `WeekTimeline.kt` не трогаем: часть занятия в скрытый день просто не рендерится, часть на видимом дне уже ограничена клиппингом span'а.

5. **Проверки — адресная ручная + существующий автотест.** Новых бизнес-правил нет: число дней — прямое следствие boolean, сохранение — штатный механизм платформы. Ручная проверка на эмуляторе Pixel 7a (TESTING.md): тумблер в настройках; сетка 7→5 столбцов; заголовки пн–пт; занятия субботы/воскресенья не видны; занятие пт 23:30→сб 01:00 видно в пятницу до полуночи; месячный режим без изменений; значение переживает перезапуск. Регрессия: `.\gradlew.bat :app:testDebugUnitTest` (`WeekTimelineTest` — единственный существующий). Новый автотест не вводится (§26).

## Risks / Trade-offs

- [Тумблер только в настройках] → путь через меню длиннее; принято решением пользователя (настройка — в разделе настроек).
- [Ночное пятничное занятие «обрезается» при скрытых выходных] → часть на пятницу остаётся видна; поведение зафиксировано в спеке (сценарий 20).
- [Новый пакет в карте] → один дополнительный `PACKAGE.md`; альтернатива (корневой пакет) отклонена по §11.
- [Автотестов на сохранение нет] → стандартное поведение SharedPreferences, ручная проверка перезапуска.
- [Карты пакетов устарели (тесты, на которые ссылаются, удалены)] → правки внятных карт (root, `ui.screen`, `schedule`) привязаны к этому изменению; чужие карты не трогаем.

## Migration Plan

Миграций данных нет: новый prefs-файл `settings`, дефолт `false` сохраняет текущее поведение. Откат — отмена коммита (Presentation + Data + карты); prefs-файл безвреден.
